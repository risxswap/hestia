# Agent SSE 实时回复流设计

## 背景

当前聊天接口已经使用 SSE，小程序也通过 `onChunkReceived` 增量解析事件，但回复正文并未实时返回。服务端在 Agent Runner 内完整消费 Eino 输出，等待模型和工具流程全部结束后才发送一次 `message` 事件。用户在这段时间只能看到处理过程，无法看到模型已经生成的回复内容。

本次改造要实现真正的内容流式输出：模型最终回复产生增量时，服务端立即通过 SSE 发送，小程序持续追加显示。用户主动停止或连接中断时，已经生成的部分回复必须保留并可从历史记录恢复。

## 目标

- 使用 Eino 原生 `MessageStream` 获取模型最终回复增量。
- 通过 SSE `delta` 事件实时传递新增文本。
- 小程序在首个增量到达后立即显示回复正文。
- 回复正文只通过 `delta` 事件传输，不在完成时重复发送完整正文。
- 用户停止、请求取消或连接断开时保存已生成的部分回复。
- 工具调用和处理过程继续来自真实 Agent 事件，不暴露隐藏推理。

## 非目标

- 不在模型完整返回后人为拆字制造打字动画。
- 不按 token 或 SSE 增量频繁写数据库。
- 不增加 SSE 自动重连或断点续传。
- 不兼容旧版 `message` 正文事件或非流式 Runner 接口。
- 不把中间工具参数、工具结果正文或模型隐藏推理发送给用户。
- 不为流式回复新增独立消息表。

## 方案选择

采用 Eino 原生流，并将 Agent 最终回复契约收敛为自然文本。

不保留“最终回复必须是 JSON，再从半截 JSON 中提取 `assistant_text`”的方案。增量 JSON 容易受到字段顺序、字符串转义、Markdown 引号和不完整结构影响，需要自研脆弱的流式 JSON 字符串解析器。工具调用继续使用模型原生 Tool Calling；工具审计以真实 ADK 事件为准，不依赖模型在最终 JSON 中再次声明。

也不采用完成后切块方案，因为它不会降低首段正文等待时间。

## 总体数据流

```text
Eino ChatModel Stream
  -> ADK AgentEvent.MessageOutput.MessageStream
  -> EinoADKAdviceRunner 逐块读取并聚合完整文本
  -> AdviceRunner 增量回调
  -> Agent Service 文本增量回调
  -> HTTP Handler 写入 event: delta 并 Flush
  -> 小程序 SSE parser
  -> 页面 50ms 合并刷新正文
```

同一条模型流只允许消费一次。Runner 在读取每个 chunk 时同时完成两件事：向上游发送文本增量，以及追加到本轮完整回复缓冲区。最终落库使用缓冲区中的完整文本。前端展示内容与服务端聚合内容来自同一组 chunk，不再使用第二条完整正文事件校准。

## Agent 最终回复契约

Agent 最终输出改为面向用户的自然文本，不再要求包含 `assistant_text`、`decision_label` 和 `tool_calls` 的 JSON。

- 工具调用继续通过 Eino Tool Calling 消息执行。
- 工具调用与结果审计从 ADK 原生事件采集。
- 最终自然文本只承担用户回复职责。
- Markdown 可以跨 chunk 分割，小程序按原始顺序拼接。
- 中间模型决策中的工具调用消息和工具结果不得作为 `delta` 发送；只有最终 assistant 文本进入正文流。

## Runner 接口

直接将 `AdviceRunner` 升级为流式接口，不保留旧的一次性返回接口。所有生产 Runner 和测试 Runner 必须显式接收文本增量回调。

流式 Runner 接收文本增量回调。回调只接收本次新增的纯文本，不接收累计文本，也不负责持久化。Runner 必须：

1. 遍历 ADK AgentEvent。
2. 识别 `MessageOutput.IsStreaming`。
3. 逐个读取 `MessageStream`，只转发最终 assistant 回复的文本 chunk。
4. 聚合 chunk 得到完整回复。
5. 从真实工具消息生成审计步骤。
6. 正常结束时返回完整输出；异常或取消时同时返回已经聚合的部分输出和错误。

模型必须通过 Eino Stream 路径执行。供应商即使只返回单个完整 chunk，也通过同一 `delta` 路径传输，不增加非流式执行分支。

## SSE 协议

新增事件：

```text
event: delta
data: {"text":"本次新增文本"}
```

事件顺序：

1. `status`
2. 零到多个 `process`
3. 零到多个 `delta`
4. 可选 `draft`
5. `done`

失败时发送 `error`。如果失败前已有正文增量，客户端保留已显示内容；服务端保存部分回复并将消息标记为失败。

Handler 每次写入 `delta` 后立即 Flush。写入失败或请求 Context 取消时，不再继续向客户端发送事件，并取消 Agent 执行。

删除现有 `message` SSE 事件及对应客户端回调。新协议不考虑旧客户端兼容，以 `delta` 为唯一正文传输事件。

## 正常完成与持久化

正常执行期间只在内存中聚合增量，不更新 `chat_msgs`。Agent、工具和业务处理完成后：

- 使用完整回复更新助手消息正文。
- 按现有逻辑关联草稿卡片和审计步骤。
- 发送 `draft` 和 `done` 完成本轮。

这样数据库写入次数不随 token 数量增长。

## 停止、断开与中途失败

新增助手消息状态 `stopped`。

### 用户停止或连接断开

- 小程序立即中止请求并保留当前已显示内容。
- 请求 Context 取消，Runner 停止读取模型流并返回部分输出。
- Service 使用 `context.WithoutCancel` 派生独立持久化 Context，并增加短超时，保存部分正文和 `stopped` 状态。
- 如果尚未产生任何正文，保存“已停止生成”作为安全占位文案。
- 已经成功执行的工具效果和审计记录保留；Context 取消后不得启动新的工具调用。

### 输出中途失败

- 已有部分正文时保存正文并标记 `failed`。
- 尚无正文时沿用现有失败兜底文案和失败状态。
- SSE 发送 `error`，不再发送成功 `done`。

独立持久化 Context 只用于保存当前助手消息和已产生的审计结果，不能继续执行 Agent、工具或草稿业务操作。

## 历史恢复

历史接口继续返回助手正文和状态：

- `stopped`：小程序显示已保存的部分正文，并将过程状态展示为“已停止”。
- `failed` 且有正文：显示部分正文和“本轮未完整完成”。
- `generating`：仍按现有逻辑显示运行中；后续可以单独处理服务进程异常留下的悬挂消息，不属于本次范围。

## 小程序处理

`api.streamAgentChat` 复用现有 SSE parser，自动将 `delta` 映射为 `onDelta` 回调。

Advisor 页面为当前请求维护内存增量缓冲：

- `onDelta` 只把 `data.text` 追加到缓冲区。
- 每约 50ms 将缓冲区合并到当前助手消息的 `content`，减少高频 `setData`。
- 收到 `done`、`error`、用户停止或页面卸载时立即清空剩余缓冲。
- 用户停止后保留现有正文，状态显示为已停止。
- 恢复历史时将服务端 `stopped` 映射为停止状态，而不是通用错误。

页面继续使用 Markdown 组件渲染累计正文。允许 Markdown 结构在生成中暂时不完整，后续 delta 到达后自然恢复。

## 错误与隐私边界

- SSE `delta` 只包含模型面向用户的最终回复文本。
- 不发送 system prompt、工具参数、工具结果正文、模型隐藏推理或原始异常。
- 失败事件继续使用用户安全文案。
- 日志只记录字符数、耗时和脱敏摘要，不逐 chunk 记录正文。
- 停止持久化失败必须记录结构化错误，但不能覆盖原始 Agent 错误。

## 测试与验证

服务端测试覆盖：

- 流式 MessageStream 的多个 chunk 按顺序回调并正确聚合。
- UTF-8 中文、Markdown 和跨 chunk 内容不丢失、不重复。
- 中间工具调用消息不作为正文增量发送。
- 单个完整模型 chunk 仍通过 `delta` 输出。
- Handler 按顺序输出 `delta`、可选 `draft` 和 `done`，不再输出 `message`。
- 用户取消后保存部分正文并标记 `stopped`。
- 连接中断后使用独立短超时 Context 完成部分持久化。
- 中途失败保存部分正文并标记 `failed`。
- 没有部分正文的失败继续使用安全兜底。
- 工具调用已经完成时，其效果和审计记录不会因停止被回滚或伪造。

小程序测试覆盖：

- API 客户端解析 `delta` 并调用 `onDelta`。
- 页面按 50ms 合并增量，正文不重复。
- `done`、`error`、停止和卸载会刷新或清理缓冲。
- 停止后保留正文。
- 历史 `stopped` 状态正确恢复。

完成后运行服务端全量 Go 测试、小程序现有验证脚本，并通过真实本地 SSE 请求确认回复正文随多个 `delta` 到达，最终以 `done` 结束。

## 验收标准

- 用户不再等待整轮 Agent 完成后才看到回复，首个模型正文 chunk 到达即开始显示。
- SSE 至少产生一个 `delta`，其拼接结果与服务端最终落库正文一致。
- 用户停止或连接断开后，已显示的部分回复在刷新历史后仍存在。
- 停止后不会继续执行新的工具调用或草稿操作。
- 流式过程不增加按 token 数据库写入，也不泄露内部 Agent 信息。
