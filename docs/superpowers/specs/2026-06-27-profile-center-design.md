# 小程序我的页面设计

## 背景

当前小程序已经有 `pages/profile`，但页面只展示本地开发登录状态、用户 public id 和 onboarding 状态，缺少真正的个人中心能力。Hestia 的第一版核心价值不是一次性测评，而是持续记忆和进化；因此“我的”不应只是传统设置页，而应成为用户查看、修正和管理个人形象档案的入口。

本设计面向微信小程序首版，把“我的”定位为形象档案仪表盘：让用户知道 Hestia 记住了什么、这些信息从哪里来、哪些可以修改、哪些可以删除。

## 目标

- 将“我的”首屏升级为个人形象档案仪表盘。
- 展示用户身份、onboarding 状态、初版报告状态和记忆摘要。
- 支持轻量编辑用户明确填写的档案、风格目标、场景偏好和禁忌。
- 区分用户明确陈述的信息和 AI 推断的信息。
- 对 AI 推断先提供展示、采纳或标记不准的轻量纠错路径。
- 提供隐私与数据管理入口，保留删除照片、档案和反馈数据的能力。
- 前端通过一个聚合摘要接口加载首屏，降低页面组装复杂度。

## 非目标

- 不把“我的”做成完整后台管理系统。
- 不在首版提供复杂的记忆编辑器、版本对比或来源图谱。
- 不展示“你像某明星”之类相貌对比结论。
- 不做会员、订单、商品推荐或电商跳转。
- 不做减肥、医疗、植发、皮肤病、整形等高风险建议入口。
- 不提供无说明的一键清空全部服务端数据操作。

## 产品定位

“我的”首版采用“个人档案优先”的方向，而不是“行动历史优先”或“设置与隐私优先”。

页面需要传达三件事：

1. Hestia 正在基于用户真实资料和反馈持续变好。
2. 用户可以查看并修正关键资料，而不是被 AI 黑箱判断。
3. 用户可以管理敏感数据，包括照片、档案和反馈。

首屏采用“档案仪表盘”结构，二级页面承载编辑和纠错。

## 首屏结构

### 顶部身份区

展示内容：

- 用户昵称。
- 用户 public id 的弱展示或调试展示。
- onboarding 状态。
- 初版报告状态。

状态文案：

- 已完成 onboarding：显示“形象档案已建立”。
- 未完成 onboarding：显示“先完成形象档案”，主操作跳转 onboarding。
- 有初版报告：显示“初版报告已生成”，可跳转报告页。
- 无初版报告：显示“生成初版报告后可查看”，不作为错误处理。

### 记忆摘要卡

卡片标题建议为“Hestia 记住了”。

展示指标：

- 明确事实数量。
- 风格偏好数量。
- 明确禁忌数量。
- AI 推断数量。
- 待确认数量。

指标表达要中性，例如“待确认 3 条”，不要使用“资料不足”“你还没完善”等焦虑式表达。

### 快捷入口

首版保留 4 个核心入口：

- 我的档案。
- 偏好与禁忌。
- 报告与路线。
- 隐私与数据。

入口需要带轻量状态文案：

- 我的档案：例如“常见场景 3 个”。
- 偏好与禁忌：例如“目标 2 · 禁忌 4”。
- 报告与路线：例如“初版报告已生成”或“暂无报告”。
- 隐私与数据：例如“照片、档案、反馈可管理”。

### 次级入口

首版可以在首屏下方展示轻量列表：

- AI 推断待确认。
- 反馈记录。
- 清除本地登录。

其中“反馈记录”如果后端历史能力不足，可以先作为占位入口或后续能力提示，不阻塞首屏上线。

## 二级能力设计

### 我的档案

展示并允许编辑用户明确填写的资料：

- 昵称。
- 性别。
- 身高。
- 身形备注。
- 肤色备注。
- 发型或发量备注。
- 常见生活场景。

编辑原则：

- 只编辑用户明确资料。
- 字段为空时使用中性空态。
- 保存失败保留用户输入。
- 不输出医疗诊断、病理判断或需要专业资质的建议。

### 偏好与禁忌

展示并允许编辑：

- 风格目标。
- 明确不喜欢或不适合尝试的方向。
- 常见场景偏好。

表达方式：

- 使用“你明确说过”承载用户陈述。
- 避免把禁忌写成身材、肤色或年龄羞辱。
- 可提供“添加一条”或“删除一条”的轻量操作。

### AI 推断

AI 推断首版只做轻量确认，不做复杂编辑器。

每条推断展示：

- 推断内容。
- 置信度或不确定性表达。
- 来源说明，例如“来自 onboarding 和最近反馈”。
- 操作：采纳、不准。

“不准”操作只表示该推断不应继续影响建议，不要求用户必须提供替代答案。后续可以扩展为“修正为指定内容”。

### 报告与路线

首版复用现有报告页能力：

- 有初版报告时跳转 `pages/report/report`。
- 无报告时展示引导，不报错。
- 路线详情仍由报告页承载，不在“我的”中重复实现。

### 隐私与数据

首版采用分区管理，避免危险的一键误删。

分区包括：

- 删除照片与上传资产。
- 删除形象档案与偏好。
- 删除反馈记录。
- 清除本地登录状态。

前三项是服务端数据删除能力，需要二次确认。第四项只清除本地 token、用户 public id 和 onboarding 状态缓存，不删除服务端数据。

危险操作确认文案必须说明影响范围，例如“这会删除你上传的照片，不会删除你的账号登录状态”。

## 小程序页面设计

页面继续使用原生小程序和现有全局样式。

设计风格应保持：

- 克制、清晰、可扫描。
- 工具型个人中心，不做营销型 hero。
- 不使用夸张装饰，不制造焦虑。
- 卡片圆角、色彩和间距沿用现有小程序。

交互建议：

- 首屏加载 summary。
- 下拉或按钮重试。
- 点击快捷入口进入二级编辑区。
- 编辑可以先用当前页面内分区或底部弹窗；若字段变多，再拆页面。
- 危险操作必须使用确认弹窗。

## 后端接口设计

### 获取个人中心摘要

`GET /api/user/profile/summary`

用途：

- 为“我的”首屏提供聚合数据。
- 避免小程序首屏同时请求 account、profile、report、wardrobe、feedback 等多个领域接口。

响应示例：

    "height_cm": 165,

  },

    {
      "key": "profile",

无档案时：

- `profile` 返回 `null`。
- `memory_summary` 数字为 0。
- `latest_report` 可以为 `null`。
- `quick_entries` 仍返回，用于渲染空态入口。

### 更新档案

`PATCH /api/user/profile`

可更新字段：

- `nickname`
- `gender`
- `height_cm`
- `body_notes`
- `skin_notes`
- `hair_notes`
- `lifestyle_scenarios`

限制：

- 只写用户明确资料。
- 不覆盖 AI 推断。
- 字段长度需要服务端校验。
- `lifestyle_scenarios` 需要限制条数和单条长度。

### 更新偏好与禁忌

`PATCH /api/user/profile/preferences`

可更新字段：

- `style_goals`
- `avoidances`
- `scenario_preferences`

实现上可以替换用户明确偏好集合，沿用 `profile_prefs` 的 positive/negative 语义。

### AI 推断反馈

`POST /api/user/profile/inferences/:public_id/feedback`

请求：

```json
{
  "action": "accept",
  "reason": ""
}
```

`action` 首版支持：

- `accept`
- `reject`

首轮实现可以先预留接口设计；如果当前 `profile_inferences` 缺少 public id 或状态字段不足，可以在计划阶段决定是否本轮落地。

### 隐私删除接口

隐私删除建议按分区设计：

- `DELETE /api/user/assets`
- `DELETE /api/user/profile`
- `DELETE /api/user/feedbacks`

如果现有领域边界尚未准备好，可以先在 spec 中保留接口契约，计划阶段拆成独立实现项。页面首版至少需要呈现入口和确认流程，不把未实现删除能力伪装成已完成。

## 数据来源

summary 接口的数据来源：

- `users`：用户 public id、昵称、onboarding 状态。
- `profiles`：基础档案。
- `profile_facts`：明确事实数量。
- `profile_prefs`：目标、偏好和禁忌数量。
- `profile_inferences`：AI 推断和待确认数量。
- `reports`：最新初版报告。

后续如反馈历史成熟，可以再纳入：

- `feedbacks`：反馈数量和最近一次反馈。
- `memories`：长期记忆统计。

首版不要求 summary 暴露所有原始明细，只返回页面首屏需要的摘要。

## 错误处理

- summary 接口失败：保留基础登录信息，展示“档案读取失败”，提供重试。
- 未登录：由现有用户 session 中间件返回未授权，小程序重新走登录或开发登录。
- 未完成 onboarding：首屏展示“先完成形象档案”，主操作跳转 onboarding。
- 无报告：报告入口显示“暂无报告”，不报错。
- 无档案字段：使用中性空态，例如“还没有记录常见场景”。
- 更新失败：保留表单输入，提示失败原因，允许重试。
- 删除失败：不改变本地展示状态，提示失败原因。

## 隐私与表达边界

- 自拍、身材、衣橱、审美偏好和反馈都视为敏感个人数据。
- 页面不使用羞辱式或焦虑式表达。
- 对身材、肤色、年龄感、脸型、发量等描述必须中性、具体、可行动。
- AI 推断必须有不确定性表达，不写成绝对判断。
- 删除类操作必须明确影响范围并二次确认。
- 清除本地登录不等于删除服务端数据，文案必须区分。

## 验证范围

### 后端

需要覆盖：

- `GET /api/user/profile/summary` 返回用户、档案、记忆摘要和报告状态。
- 用户无档案时 summary 返回稳定空态。
- 用户无报告时 summary 不报错。
- 未登录请求被拦截。
- `PATCH /api/user/profile` 校验字段长度、场景条数和用户归属。
- `PATCH /api/user/profile/preferences` 正确更新用户明确偏好和禁忌。

若本轮落地 AI 推断反馈和隐私删除，还需要覆盖：

- 推断采纳或拒绝只影响当前用户的数据。
- 分区删除只删除指定类型数据。
- 删除接口具备幂等或稳定失败语义。

### 小程序

需要覆盖：

- profile 页面加载 summary 并渲染仪表盘。
- loading、失败、未完成 onboarding、无报告、无档案空态。
- 快捷入口跳转或打开对应编辑区。
- 档案编辑保存成功后刷新 summary。
- 档案编辑保存失败后保留用户输入。
- 偏好与禁忌编辑保存成功后刷新 summary。
- 隐私删除入口有明确二次确认。
- 清除本地登录只删除本地缓存。

### API 客户端

需要覆盖：

- `getProfileSummary` 请求路径。
- `updateProfile` 请求路径和方法。
- `updateProfilePreferences` 请求路径和方法。
- 接口错误能透传到页面。

## 已确认决策

- “我的”首版定位为个人形象档案仪表盘。
- 首屏采用档案仪表盘，而不是纯记忆清单或普通设置列表。
- 用户明确资料支持轻量编辑。
- AI 推断首版只做展示、采纳或标记不准。
- 首屏通过 `GET /api/user/profile/summary` 聚合加载。
- 更新档案和偏好使用独立接口。
- 隐私与数据采用分区管理，危险操作需要二次确认。
