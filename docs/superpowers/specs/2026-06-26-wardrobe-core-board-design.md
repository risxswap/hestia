# 核心衣橱管理页设计

## 背景

Hestia 当前小程序已经有 `pages/wardrobe`，但页面只展示初版报告里的衣橱缺口，还不能管理用户真实拥有的核心单品。服务端已经有 `wardrobe_items`、`wardrobe_item_assets` 和 `wardrobe_gaps` 表，onboarding 提交时也会写入核心单品，但缺少用户侧的列表、增删改、图片绑定和推荐可用性管理。

本设计将衣橱页完善为“核心单品板”：只管理会影响后续建议的高频、关键单品，不做完整库存系统，也不做电商导购。

## 目标

- 用户可以查看、添加、编辑和删除核心衣橱单品。
- 用户可以为每件单品可选绑定 1 张主图。
- 用户可以标记单品的推荐可用性：高频核心、可参考、暂不推荐。
- 衣橱页保留“建议补齐”区块，展示报告识别出的缺口单品，但不提供具体商品链接。
- 衣橱更新只影响之后的每日建议和对话建议，不自动重算初版报告。
- 保留日常软删除和隐私级清除衣橱数据的产品能力边界。

## 非目标

- 不做完整衣橱库存管理。
- 不做批量衣橱照片识别。
- 不做穿着次数、购买时间、价格、清洗维护等库存字段。
- 不做 SKU 推荐、商品链接或电商跳转。
- 不自动重算已有初版报告。
- 不把缺口单品混入“已拥有单品”列表。

## 页面设计

衣橱页第一屏是“核心衣橱”工作台，不是库存总览。

页面结构：

1. 顶部标题区
   - 标题：核心衣橱。
   - 副文案：展示会影响建议的核心单品数量。
   - 主操作：新增。

2. 建议参考摘要
   - 展示“之后建议会优先参考”的若干单品。
   - 来源为当前 active 且非 paused 的核心/高频单品。
   - 用轻提示表达，不承诺一定每次推荐。

3. 分类筛选
   - 分类包括：全部、上衣、下装、外套、鞋、包、配饰。
   - 第一版只做单选筛选，不做复杂组合筛选。

4. 单品卡片
   - 展示主图或占位图。
   - 展示名称、类别、颜色/特征。
   - 展示推荐状态标签：高频核心、可参考、暂不推荐。
   - 展示适用场景标签，例如通勤、约会、周末。
   - 点击进入编辑。

5. 建议补齐区块
   - 位于单品列表之后。
   - 展示最新报告中的 `wardrobe_gaps`。
   - 文案强调这是“建议补齐”，不是已拥有单品。
   - 不展示商品链接。

空状态：

- 无核心单品时展示“先添加 1 件常穿单品”。
- 主入口为手动新增。
- 照片只是新增表单里的可选项，不阻塞保存。

## 新增与编辑流程

新增单品以手动录入为主，单品照片可选。

表单字段：

- 名称：必填。
- 类别：必填，默认上衣。
- 颜色或特征：可选。
- 版型：可选。
- 材质：可选。
- 季节：可选。
- 适用场景：可选，多选或标签输入。
- 推荐状态：默认可参考。
- 是否核心：默认开启。
- 备注：可选。
- 主图：可选，最多 1 张。

编辑流程复用新增表单。

删除单品时，普通删除为软删除：

- 页面不再展示。
- 后续建议不再读取。
- 后端保留历史，避免旧建议、反馈和报告快照失去解释基础。

恢复能力可以放在后续版本；第一版不需要提供“回收站”。

## 后端接口

新增 wardrobe 用户路由组：

`/api/user/wardrobe`

### 查询单品

`GET /api/user/wardrobe/items`

查询参数：

- `category`：可选。
- `recommendation_status`：可选。
- `is_core`：可选。

默认返回当前用户未软删除的单品。

响应中每个单品包含：

- `public_id`
- `name`
- `category`
- `color`
- `silhouette`
- `material`
- `season`
- `scene_tags`
- `user_notes`
- `is_core`
- `recommendation_status`
- `status`
- `primary_image`
- `created_at`
- `updated_at`

### 新增单品

`POST /api/user/wardrobe/items`

请求字段：

- `name`
- `category`
- `color`
- `silhouette`
- `material`
- `season`
- `scene_tags`
- `user_notes`
- `is_core`
- `recommendation_status`
- `primary_asset_public_id`

校验：

- `name` 必填。
- `category` 必填；为空时服务端可兜底为 `unknown`，但前端应给出默认值。
- `recommendation_status` 只能是 `preferred`、`normal`、`paused`。
- `primary_asset_public_id` 必须属于当前用户。

### 编辑单品

`PATCH /api/user/wardrobe/items/:public_id`

支持局部更新。

如果更新 `primary_asset_public_id`：

- 新资产关联为主图。
- 旧主图取消主图或移除关联。
- 第一版每件单品只展示一张主图。

### 删除单品

`DELETE /api/user/wardrobe/items/:public_id`

语义：

- 设置 `status=deleted`。
- 设置 `deleted_at`。
- 不物理删除数据库行。
- 后续建议上下文不再读取该单品。

### 隐私级清除

保留整体接口设计：

`DELETE /api/user/wardrobe`

语义：

- 清除当前用户衣橱单品、单品图片关联和衣橱缺口。
- 相关图片资产进入删除或不可用状态。
- 该能力可以先在 spec 中定义，不强制和本轮页面同时完成入口。

## 数据模型

扩展 `wardrobe_items`：

- 新增 `recommendation_status varchar(32) NOT NULL DEFAULT 'normal'`

推荐状态：

- `preferred`：高频核心，建议优先参考。
- `normal`：可参考。
- `paused`：拥有但暂不推荐。

继续使用已有字段：

- `status` 表示生命周期状态，例如 `active`、`deleted`。
- `is_core` 表示是否核心单品。
- `scene_tags` 存储适用场景 JSON 数组。
- `wardrobe_item_assets` 存储单品与图片资产关系。

字段语义：

- `status=deleted`：页面不展示，建议不读取。
- `recommendation_status=paused`：页面展示，但建议不读取。
- `recommendation_status=preferred`：建议上下文优先排序。
- `is_core=true`：进入核心衣橱统计和摘要。

图片关系：

- 每件单品第一版最多展示一张主图。
- 关联表继续用 `wardrobe_item_assets`。
- `is_primary=1` 的关联作为 `primary_image` 返回。
- 无主图时前端展示占位块。

## 建议上下文

衣橱更新只影响之后的每日建议和对话建议，不自动重算初版报告。

构造建议上下文时：

- 读取 `status=active` 的单品。
- 排除 `recommendation_status=paused`。
- `recommendation_status=preferred` 优先。
- `is_core=true` 优先。
- `scene_tags` 与当前场景匹配时优先。
- 控制上下文长度，只放最相关的核心单品。

初版报告：

- 已生成报告的 `context_snapshot` 不回写。
- 用户之后修改衣橱，不改变历史报告内容。
- 报告页继续展示生成时的结果。

## 缺口单品

衣橱页保留“建议补齐”区块。

数据来源：

- 第一版可以继续从最新报告的 `content_json.wardrobe_gaps` 派生。
- 后续可接入 `wardrobe_gaps` 表的独立查询接口。

展示要求：

- 不与已拥有单品混排。
- 不提供商品链接。
- 文案强调“补齐方向”而不是“必须购买”。
- 用户已经新增相近单品后，后续建议逻辑可以减少同类缺口的出现，但本轮不要求自动消除缺口。

## 隐私与表达

- 衣橱文字、照片和反馈都视为敏感个人数据。
- 普通删除采用软删除，以保护历史建议解释能力。
- 需要保留隐私级清除能力，允许用户清除衣橱数据和图片关联。
- 页面表达避免焦虑感，不使用“缺陷”“必须买”等措辞。
- 对身材、肤色、年龄感、发量等内容不在衣橱页做评价。

## 错误处理

前端：

- 列表加载失败时展示可重试文案。
- 新增或编辑失败时保留表单内容。
- 图片上传失败不影响文字单品保存，除非用户明确选择“只保存带图单品”。
- 删除失败时不从本地列表移除。

后端：

- 非本人单品返回 404 或权限错误，不泄露资源存在性。
- 非法 `recommendation_status` 返回校验错误。
- 非本人 `primary_asset_public_id` 返回校验错误。
- 已软删除单品再次删除应保持幂等。

## 测试范围

后端：

- repository/service 测试：新增、列表、编辑、软删除、主图关联。
- 状态校验测试：只允许 `preferred`、`normal`、`paused`。
- 路由测试：用户只能访问自己的单品。
- 建议上下文测试：`paused` 不进入上下文，`preferred` 排在 `normal` 前。

小程序：

- API client 验证：衣橱接口路径、请求 payload、错误归一化。
- 页面逻辑验证：列表加载、分类筛选、新增/编辑表单、主图可选、停用/恢复、缺口展示。
- 空状态验证：无单品时引导新增；最新报告无缺口时展示温和空文案。

## 实现决策

- 本轮优先完成单品列表、新增、编辑、软删除、推荐状态和主图关联。隐私级 `DELETE /api/user/wardrobe` 写入接口设计，但不作为页面首轮必需入口。
- 主图能力以 `primary_asset_public_id` 绑定为后端核心能力。若现有小程序图片上传链路不足，本轮前端可先展示无图占位和已有关联图，上传入口作为后续独立增强。
- 建议上下文先在后端提供可复用的查询/排序能力。具体接入每日建议或对话建议的位置，在实现计划阶段结合现有 agent/advisor 代码落点确定。
