# 新增衣服图片识别回填设计

## 背景

当前“我的衣服”新增弹窗已经支持上传主图，但用户仍需要手动填写名称、分类、颜色、廓形、材质、季节和场景。对普通用户来说，这些字段适合由图片识别先给出初稿，再由用户确认修正。

## 目标

- 新增衣服时，主图上传区域放在表单最前面。
- 用户上传主图成功后，系统调用大模型识别图片中的衣服信息。
- 识别结果主动回填到表单草稿，减少用户输入。
- 回填只填空字段，不覆盖用户已经手动输入的内容。
- 识别失败不阻塞手动填写、图片绑定和保存。

## 非目标

- 不做上传即创建衣服。
- 不做批量衣橱图片识别。
- 不做电商 SKU、商品链接或品牌价格识别。
- 不保证识别结果完全准确，用户保存前仍可编辑。
- 不使用未经授权的外部图片抓取能力。

## 交互设计

新增弹窗打开后，表单顺序调整为：

1. 主图上传。
2. 名称、分类、颜色、廓形、材质、季节。
3. 适用场景、备注、推荐状态、核心单品。

上传主图成功后：

- 上传组件显示缩略图。
- 页面进入“正在识别图片”状态。
- 小程序调用衣橱图片识别接口。
- 识别完成后，将识别字段合并进当前草稿。
- 合并规则是只填空字段：如果用户已经填写或修改某字段，识别结果不能覆盖。

识别失败时：

- 显示轻量错误提示，例如“图片已上传，识别失败，可手动填写”。
- 保留已上传图片和 `primary_asset_public_id`。
- 保存按钮仍可用，只要必填字段满足现有规则。

编辑已有衣服时：

- 主图仍在最前面。
- 替换图片后也可以触发识别回填。
- 仍遵守只填空字段，避免覆盖已有单品信息。

## 后端设计

在受登录保护的衣橱用户路由下新增接口：

`POST /api/user/wardrobe/items/recognize`

请求体：

```json
{
  "asset_public_id": "ast_xxx"
}
```

响应体：

```json
{
  "name": "米白针织开衫",
  "category": "outerwear",
  "color": "米白",
  "silhouette": "微宽松",
  "material": "针织",
  "season": "春秋",
  "scene_tags": ["通勤", "周末"],
  "user_notes": "建议内搭简洁上衣，避免叠加过多厚重层次",
  "confidence": 0.78
}
```

服务端行为：

- 校验用户已登录。
- 校验 `asset_public_id` 非空，且资产应属于当前用户的衣橱图片。
- 第一版接口返回结构化候选字段，不直接写入衣橱单品。
- 大模型输出必须限制在衣服相关字段，避免输出身材、长相、医疗或焦虑化判断。
- 如果识别能力未配置或调用失败，返回明确错误码，由前端降级为手动填写。

## 前端设计

小程序 API 层新增：

- `recognizeWardrobeItemImage(assetPublicID)`

衣橱页新增状态：

- `imageRecognizing`
- `imageRecognizeError`

上传成功流程：

1. `uploadAssetToQiniu` 返回资产。
2. 写入 `draft.primary_asset_public_id` 和 `imageFiles`。
3. 调用 `recognizeWardrobeItemImage(uploaded.asset_public_id)`。
4. 将识别结果按只填空字段合并进 `draft`。
5. 如果识别结果含 `scene_tags`，仅当 `draft.sceneText` 和 `draft.scene_tags` 为空时回填。

## 验证

- 后端 service 测试覆盖识别请求校验、字段修剪和识别结果归一化。
- 后端 routes 测试覆盖识别接口成功和参数缺失错误。
- 小程序验证脚本覆盖：
  - 主图上传区域出现在名称输入前。
  - API 客户端暴露识别接口。
  - 上传成功后触发识别。
  - 识别结果只回填空字段，不覆盖已有字段。
